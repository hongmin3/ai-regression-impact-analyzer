# QA 자동화 플랫폼 공용 아키텍처

## 현재 판단

새 QA 프로그램은 별도 웹서비스나 별도 DB부터 만들지 않고, 현재 FastAPI 애플리케이션의
`app/modules/<module_name>/` 아래에 기능 모듈로 추가한다. 루트(`/`)는 기능 선택 허브이며,
각 모듈은 고유 URL prefix와 자신의 라우터·서비스·템플릿·테스트를 소유한다.

SQLite 파일은 당분간 하나를 공유하되 **테이블 소유권은 모듈 단위로 분리**한다.
공유 식별자(제품, 문서, 분석 실행)만 공용 테이블을 재사용하고, 기능 고유 데이터는
`manual_*`처럼 충돌하지 않는 접두어를 사용한다. 모듈 간 DB 테이블을 직접 조작하지 않고
`app/core/storage.py`의 명시적인 메서드를 통해 접근한다.

## 경계

- `app/core/`: 설정, 저장소, 로깅, AI 호출, 스케줄러처럼 도메인에 독립적인 인프라
- `app/web/`: 허브, 공용 레이아웃·정적 파일, 모듈 라우터 취합
- `app/modules/impact_analyzer/`: Regression 영향 분석
- `app/modules/manual_review/`: 매뉴얼 개정 검증
- `app/prompts/`: 버전 관리되는 기능별 AI prompt

## DB 확장 원칙

1. 공통 제품과 업로드 문서는 기존 `products`/`documents`를 재사용한다.
2. 기능 전용 상태와 결과는 해당 모듈 전용 테이블에 둔다.
3. 테이블 추가·변경은 반복 실행 가능한 migration 방식으로 관리한다. 현재의
   `CREATE TABLE IF NOT EXISTS`/컬럼 보강 방식은 소규모 단일 서버 동안만 유지하고,
   운영 인스턴스나 개발자가 늘어나는 시점에는 Alembic 같은 버전 migration으로 전환한다.
4. SQLite WAL과 단일 프로세스는 현재 부하에 적합하다. 동시 쓰기 증가, 다중 worker,
   여러 서버 배포 중 하나가 필요해지면 PostgreSQL로 이전한다.
5. 비밀정보, 업로드 원본, 생성 결과물은 DB에 본문으로 넣지 않고 현재처럼 설정된 파일
   저장소에 보관하며 DB에는 경로와 metadata만 저장한다.

## 새 QA 모듈 추가 체크리스트

1. `app/modules/<name>/`에 router/service/schema/template을 추가한다.
2. `app/web/router.py`에서 충돌 없는 prefix로 등록한다.
3. 공용 데이터와 전용 데이터를 구분해 Storage API와 migration을 추가한다.
4. 허브 카드와 공용 내비게이션, 사용법을 갱신한다.
5. 라우트·저장소·도메인 단위 테스트와 전체 회귀 테스트를 통과시킨다.
6. 로컬 검증 후 배포 스크립트로 동일 파일을 서버에 반영한다.

이 구조는 기능 수가 적은 현재 단계에서 배포·운영을 단순하게 유지하면서도, 향후 부하나
조직 경계가 실제로 생겼을 때 모듈을 별도 서비스와 DB로 분리할 수 있는 경계를 보존한다.
